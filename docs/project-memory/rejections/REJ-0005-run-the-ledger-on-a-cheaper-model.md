# REJ-0005: Run the ledger on a cheaper model, in a subagent

## What was proposed
Pin the `decision-ledger` skill to the smallest available model via frontmatter
(`model: haiku`) and run it as a subagent, optionally in the background, so that
record-writing does not consume the main session's budget.

The mechanism is real and was verified, not assumed: skill frontmatter supports
`model`, `effort`, `agent`, `context` and `background`. Nothing about this
proposal was technically impossible.

## Discussion
The instinct behind it is sound and is applied elsewhere in this project: push
mechanical work to the cheapest tier that can do it. The owner raised it as a
token-saving measure after the plugin's cost was measured at roughly 1,892
resident tokens per session.

## Why it was rejected

**It does not save tokens.** The resident cost is the SessionStart briefing
(~1,490 tokens) plus the skill listings (~401). The briefing is generated by a
Python hook, so no model produces it and every model pays the same to receive
it; the listings are resident so the model knows the skill exists at all. Model
choice changes price per token, not token count. Since the proposal was made
specifically to save tokens, it does not do the thing it was for.

**It cheapens the only part that cannot be cheapened.** The value of a record
is concentrated in three sections: Reasoning, Cost and Re-evaluation trigger.
Each is synthesis under judgement, which is the first capability to degrade on a
smaller model. A weak model emits "Chose Parquet because it is better for large
files" — a record that satisfies the schema and fails the bar. The outcome is
paying for the whole apparatus and accumulating records that do not carry
reasoning, which is worse than having no ledger, because it looks like one.

**The subagent cannot win either way.** A fresh subagent starts without the
conversation that contains the decision, so the context must be handed to it,
costing more than writing the record inline. A forked subagent inherits the
conversation but then re-processes all of it on the second model, which for a
long session is likely more expensive than what it replaced.

**Background execution risks silent loss.** An async write as a session ends may
never land, and the failure is silent — striking exactly the mechanism built to
prevent silent loss.

## What was done instead
The division already in place and kept: mechanical work to scripts, judgement to
the best available model. ID allocation, collision avoidance, index generation,
the activity trail, git inspection and the briefing all run as Python at zero
model cost — cheaper than any small model, and deterministic.

Measured for the record: ~1,892 tokens resident per session, under 1% of a 200k
context, growing ~17 tokens per additional record. Token cost was not the
problem the proposal assumed it was.

## Re-evaluation trigger
Revisit for `cold-start` specifically — it is read-and-relay with modest
synthesis and is the most defensible candidate — if its cost ever becomes
material. Do not revisit for `decision-ledger` itself on cost grounds alone;
only a smaller model that demonstrably writes an adequate Reasoning section
would change this, and that is a quality judgement, not a price one.
